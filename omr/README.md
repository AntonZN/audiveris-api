# `omr` — подготовка фотографий нот к распознаванию

Отдельный, самостоятельный пайплайн: **фотография → ровный лист → MusicXML**.
Ничего не импортирует из `api/`, ничего оттуда не наследует и не трогает
Audiveris. Движок распознавания — [homr](https://github.com/liebharc/homr),
подключён одним модулем (`omr/engines/homr_engine.py`) и заменяем.

```
python -m omr photo.jpg -o out/ --debug        # подготовить и распознать
python -m omr score.pdf -o out/                # PDF — тем же путём, постранично
python -m omr photos/ -o out/ --prepare-only   # только выпрямить лист
python -m omr.bench photos/ -o bench/          # замерить: как есть vs пайплайн
```

---

## Зачем это вообще

Наблюдение, с которого всё началось: на телефонных снимках наш результат хуже,
чем у сайта той же библиотеки. Мы отдавали homr снимок **как есть** — весь путь
подготовки в `api/` (`_preprocess_image`, `image_prep.enhance_for_omr`) написан
под Audiveris и в ветку homr не заходит вообще.

Дальше — что обнаружилось в исходниках самого homr и почему это решает дело.

### 1. homr ужимает вход до ФИКСИРОВАННОЙ ширины 1920 px

`homr/resize.py`:

```python
def calc_target_image_size(width, height):
    target_width = 1920
    ...
```

Это происходит **до** сегментации, то есть до того, как модель вообще увидит
страницу. Следствие прямое: любой пиксель, потраченный на стол вокруг листа, —
это пиксель, отнятый у нотных линеек. Если лист занимает половину кадра, движок
работает по странице шириной 960 px вместо 1920 — вдвое меньше деталей на тех же
нотных головках, и никакое качество сенсора этого не вернёт.

Отсюда цель пайплайна формулируется предельно конкретно: **отдать движку кадр,
в котором лист занимает ровно 1920 px и лежит ровно**.

### 2. Собственный `autocrop` в homr сдаётся как раз на телефонных снимках

`homr/autocrop.py` ищет самый большой контур и обрезает по его bounding box.
Но заканчивается это так:

```python
is_full_page_view = x < page_width * 0.25 or y < page_height * 0.25
if is_full_page_view:
    return img
```

То есть если контур страницы начинается ближе четверти кадра к краю — а именно
так выглядит нормальный снимок «лист во весь экран» — обрезка не делается вовсе.
А когда делается, это осепараллельный прямоугольник: перспективу он не правит.

### 3. Выпрямление кривизны в homr есть, но включается слишком поздно

`homr/staff_parsing.py` дewarp'ит **каждый стан отдельно**, уже после того как
станы найдены (`detect_staff`). Логика правильная, но порядок такой, что
страница, изогнутая настолько, что станы не собрались, до дewarp'а не доживает:
`raise Exception("No staffs found")`.

Значит, выпрямлять надо **до** движка, на уровне всей страницы.

### 4. Бинаризовать вход нельзя

В `api/image_prep.py` есть рецепт с adaptive threshold — он подобран под
Audiveris и там работает. Для homr он вреден: сегментация homr — свёрточная сеть,
обученная на естественных изображениях, и чёрно-белая маска для неё вход не из
распределения. Здесь порог используется только внутри, чтобы мерить геометрию;
движку уходит нормальная полутоновая картинка.

## Пайплайн

```
                        ФОТО
                          |
              [0] чтение + EXIF-ориентация
                          |
              [1] нотные линейки -> станы -> интервал
                    (на уменьшенной копии)
                          |
             [1.5] не лежит ли страница на боку (90°)
                          |
              [1.7] разворот книги? -> разрез по корешку,
                    дальше каждая половина отдельно
                          |
              [2] четырёхугольник страницы
                     /            \
              по контуру      по нотным линейкам
                     \            /
                  гомография, warpPerspective
                          |
              [3] dewarp по форме линеек (изгиб книги)
                          |
              [4] доворот по медианному углу линеек
                          |
              [5] выравнивание света + масштаб под движок
                          |
                     ЧИСТЫЙ ЛИСТ
```

Сквозная идея — **нотные линейки как калибровочная сетка**. У нотного листа есть
то, чего нет у обычного документа: пять длинных параллельных равноудалённых
линий, нанесённых прямо на бумагу. По ним считается всё: перекос, границы
страницы, кривизна, масштаб. Поэтому детектор линеек (`omr/staff.py`) один, а
стадии — его потребители.

| стадия | файл | что делает |
|---|---|---|
| 0 | `stages/load.py` | чтение, EXIF-ориентация, HEIC через Pillow |
| 1 | `staff.py` | линейки → станы → межлинейный интервал |
| 1.5 | `stages/orient.py` | поворот на 90°, если так станов находится больше |
| 1.7 | `stages/spread.py` | разворот книги -> две страницы (разрез по корешку) |
| 2 | `stages/page.py`, `stages/rectify.py` | четырёхугольник страницы и `warpPerspective` |
| 3 | `stages/dewarp.py` | `remap` по полю смещений, снятому с линеек |
| 4 | `stages/deskew.py` | доворот на медианный угол линеек |
| 5 | `stages/normalize.py` | деление на фон + масштаб под 1920 px |

Все пороги — в `config.py`, одним dataclass'ом.

### Страница на боку — половина реальных провалов

Стадия `orient` появилась не из общих соображений. Разбор архива провалов прода
(`failures_dir`, разложен в `fail_prod_files/`) дал такую картину: из 21 картинки
**пять оказались повёрнуты на 90°** — лист положили в сканер боком или сняли
телефоном с поворотом. Линейки при этом вертикальные, движок не находит ни одного
стана и падает. Это самый частый одиночный класс отказа в наборе.

Ни один другой механизм этого не ловит: оценка перекоса ищет угол в пределах
±12°, а поиск страницы по линейкам на повёрнутом листе просто не находит линеек.
Поэтому проверка стоит первой, до всей геометрии, и критерий у неё прямой:
развернуть копию на 90° и посмотреть, где станов собирается больше. Никаких
эвристик про соотношение сторон — альбомная партитура бывает, а вот стан,
лежащий на боку, не бывает.

**Куда поворачивать — отдельный вопрос, и он неочевиден.** По часовой и против
часовой дают одинаково горизонтальные линейки: эти два варианта отличаются ровно
на 180°, и детектор станов их не различает. Поворот вслепую угадывает сторону
примерно в половине случаев, а промах означает страницу вверх ногами — движок
на такой выдаёт мусор, хотя станы «нашлись».

Различаем по началу стана: там стоит ключ со знаками, и он закрывает почти всю
высоту стана подряд, чего на правом конце (одна тактовая черта) не бывает
никогда. Меряем не плотность чернил, а ДОЛЮ СТРОК полосы, в которых чернила есть:
на рукописной странице правый конец бывает чернее левого, и плотность врёт
(проверено на `rot90-03-soranji` — по плотности он уезжал вверх ногами). Считать
второй раз ничего не надо: поворот на 180° меняет левый край с правым, значит для
второй стороны оценка просто меняет знак.

Признак слабый, и это стоит помнить: на пяти сайдвейс-снимках из архива провалов
он даёт 5 из 5 против 3 из 5 у слепого поворота, но у половины запас в районе
0.01-0.07. Оценка выводится в отчёт стадии — если страница приедет вверх ногами,
сразу видно, что виновата именно эта развилка.

Чего стадия НЕ умеет: развернуть страницу, пришедшую вверх ногами БЕЗ поворота на
90°. Признак тот же, но там мы бы переворачивали изначально нормальный кадр по
слабой эвристике, а цена ошибки выше.

### Разворот книги — резать по корешку

Две страницы в одном кадре — это не «страница побольше», а два отдельных случая
сразу.

Во-первых, **масштаб**. Станов вдвое больше, и все они делят одну и ту же
целевую ширину движка: на `spread-01-trombone.png` после приведения к 1920 px на
межлинейное расстояние оставалось 6.5 px вместо нормальных 15-20. Пайплайн это
честно писал в отчёт (`стан слишком мелкий`), но починить не мог.

Во-вторых, **геометрия**. Разворот — это не одна плоскость: половины лежат под
разными углами. Одна гомография на обе принципиально не может выпрямить обе.

Разрез снимает и то и другое: каждая половина получает свои 1920 px, свою рамку,
свою гомографию и свой dewarp.

**Как ищется корешок.** По профилю покрытия колонок нотными линейками: у корешка
линейки обрываются, и в середине кадра образуется провал. Тонкость, без которой
ничего не работает: мерить надо **по сырым фрагментам, ДО склейки**.
`merge_fragments` спокойно перемахивает через корешок — на плоском скане станы
обеих страниц стоят на одной высоте, и фрагменты слева и справа выглядят как одна
разорванная линейка. Разница на реальных файлах:

| файл | по фрагментам | после склейки |
|---|---|---|
| `spread-01` (разворот) | **0.02** | 0.82 |
| `book-02` (разворот) | **0.02** | 0.51 |
| `scan-01` (одна стр.) | 0.93 | 0.95 |
| `phone-01` (одна стр.) | 0.90 | 0.95 |

По фрагментам развороты и одиночные страницы разделяются без перекрытия — порог
0.25 берётся с огромным запасом. На всём наборе провалов детектор нашёл все
четыре разворота (провал 0.00-0.06) и не тронул ни одной одиночной страницы
(0.58-1.00).

Лежащий на боку разворот сюда не попадёт: у него линейки вертикальные, детектор
их не найдёт и честно скажет «фрагментов мало». Это безопасный отказ — разворот
останется неразрезанным, но хуже не станет.

**Что даёт разрез.** Прогон по всем разворотам из архива провалов:

| файл | без разреза | с разрезом |
|---|---|---|
| `spread-01-trombone` | 63 такта, 261 нота | **117 тактов, 480 нот** |
| `book-03-annotated-notebook` | 90 тактов, 268 нот | **135 тактов, 377 нот** |
| `book-02-trumpet-tune` | 47 тактов, 183 ноты | 36 тактов, **330 нот** |
| `book-01-steep-angle` | 46 тактов, 301 нота | половина не распозналась -> откат |

Обратите внимание на `book-02`: тактов стало МЕНЬШЕ, а нот почти вдвое больше.
Число тактов на развороте вообще не метрика — до разреза homr сшивал системы
левой и правой страницы в одну (в логе 14 «систем» на разворот против 4 и 5 на
половинах) и терял при этом основную часть нот. Мерить надо по нотам.

**Откат.** Если хотя бы одна половина не распозналась, лист переобрабатывается
целиком и берётся неразрезанный результат: разрез задуман как улучшение, и
ломать им то, что работало, нельзя. Ровно этот случай — `book-01`, где левая
половина снята почти с ребра и homr на ней говорит «No staffs found».

### Как ищется страница

Два независимых оценщика:

* **по контуру** — классический «сканер документов»;
* **по нотным линейкам** — левые концы всех линеек лежат на одной прямой, правые
  на другой, крайние линейки задают верх и низ.

Второй лучше, и не только потому, что надёжнее. Нас интересует не лист бумаги, а
прямоугольник, в который вписаны станы: именно он должен стать прямоугольным и
именно на него надо потратить все 1920 px. Он же переживает случаи, где контурный
оценщик бессилен: лист без полей в кадре, разворот книги, белая бумага на белом
столе. Контур остаётся запасным вариантом, кадр целиком — последним.

Тонкость, на которой пайплайн ошибался, пока не была поправлена: боковые края
надо проводить по **внешним** концам линеек, а не «в среднем». Ошибки концов
односторонние — у первой системы левый край отступлен, последняя система
обрывается на середине строки, у сгиба детектор теряет хвост линейки, — и любая
усредняющая оценка систематически срезает музыку (`geometry.fit_edge_line`).

### Как снимается кривизна

Гомография выпрямляет плоскость; страница раскрытой книги плоскостью не является.
Полноценный document dewarping восстанавливает 3D-поверхность листа — нам это
не нужно, потому что **нотные линейки и есть линии сетки на этой поверхности**.
Строка текста задаёт свою форму только базовой линией; стан даёт пять
параллельных кривых через всю страницу.

Поэтому: берём каждую линейку как ломаную `y(x)`, считаем её отклонение от
собственной «ровной» высоты, интерполируем поле смещений по вертикали между
линейками, делаем один `remap`. Плюс поправка по длине дуги вдоль X — у сгиба
линейка длиннее своей хорды ровно во столько раз, во сколько там сжат
горизонтальный масштаб.

Решение «гнуть или не гнуть» принимается по **медиане профилей всех линеек**:
настоящий изгиб бумаги гнёт их одинаково, а ошибки детектора в медиане гасятся.
Без этого пайплайн «выпрямлял» идеально плоские сканы, теряя резкость на ровном
месте.

### Как детектируются линейки

Линейку выделяет морфологическое открытие длинным горизонтальным ядром — но у
этого приёма встроено допущение, что линейка прямая и горизонтальная. Наклон θ
уводит её на `L·sin θ` по длине ядра `L`, и уже при 8° это больше толщины
штриха: ядро рубит линейку на куски, а вместе с ней уезжает правый край блока
нот.

Поэтому разбор идёт **по вертикальным полосам**: в каждой полосе кривая линейка
почти прямая, так что достаточно оценить локальный угол (projection profile),
выпрямить сдвигом и открыть ядром уже честно. Полосы идут внахлёст, обратно их
сшивает `merge_fragments`. Изгиб страницы обрабатывается не «вопреки», а штатно.

Ещё две мины, каждая из которых по отдельности рушила весь разбор:

* **Никакой изотропной чистки шума.** Открытие даже ядром 2×2 стирает самые
  тонкие линейки — ровно по одной на стан, из-за чего пятёрки перестают
  собираться и станов находится вдвое меньше.
* **Хвосты линеек надо дотягивать.** Морфология находит уверенное «тело»
  линейки, но обрывает её там, где кривизна круче всего, — то есть у корешка.
  Потеря односторонняя, и по этим концам строится боковой край страницы, так что
  вместе с хвостами наружу уезжает последний такт каждой системы.
  `extend_lines` дотягивает линейку по одному пикселю, пока под предсказанной
  точкой есть чернила.

И одно правило сравнения: линейки сравниваются между собой **в общем X**, а не по
медианному Y своей ломаной. На изогнутом листе Y зависит от того, где мерить, а
после дотягивания хвостов линейки ещё и покрывают разные участки страницы.

### Почему пайплайн не может сделать хуже

Каждая стадия умеет отказаться («не уверен — не трогаю») и пишет в отчёт, почему.
В конце число собранных станов на выходе сверяется со входом, и если стало
заметно хуже — результат откатывается на простой вариант без геометрии
(`safety_check`). Дополнительно `--raw` прогоняет снимок мимо пайплайна: это
контрольный вариант для `omr.bench`.

## PDF идёт тем же путём

PDF не выделен в отдельный маршрут: он растеризуется постранично, и каждая
страница проходит ровно тот же пайплайн, что и снимок. Это не косметика ради
единообразия — так чинится конкретный отказ.

**Что было.** Audiveris обрабатывает PDF книгой целиком, и одна страница без нот
обнуляет экспорт ВСЕЙ книги. Замерено на реальном `pdf-02-piano-duet.pdf`:

```
листы 1-4:  LOAD -> ... -> PAGE, интерлиньяж 20-21, по 10 кластеров из 5 линеек
лист 5:     колофон с копирайтом, без единой ноты -> встаёт на шаге SCALE
выход:      только .omr и .log, НИ ОДНОГО .mxl
```

Audiveris при этом завершается с кодом 0 — он не сигнализирует об ошибке, просто
молча не экспортирует. В проде это `No MusicXML output found` и задача в архив
провалов. Убираем пятую страницу вручную — получаем 102 такта и 690 нот. То есть
целая партитура терялась из-за служебного листа. Случай массовый: у второго PDF
из набора обложка стоит первой страницей.

**Что стало.** Постранично страница без станов просто пропускается, причём
опознаёт её сам пайплайн — по нулю собранных станов, ничего дополнительного
считать не нужно:

```
стр.1: ок, движок 8s        стр.4: ок, движок 11s
стр.2: ок, движок 9s        стр.5: пропущена — нотных станов не найдено
стр.3: ок, движок 13s       склейка: страниц 4, партий 1, тактов 102
```

102 такта — ровно столько же, сколько Audiveris даёт на том же PDF с вручную
удалённым колофоном. Нот при этом 766 против 690, и результат принимается
verovio.

Растеризатор — `pypdfium2`: разрешительная лицензия и самодостаточные wheel'ы,
никаких системных пакетов в образе (в отличие от poppler/pdf2image). DPI не
фиксированный, а считается из размера конкретной страницы так, чтобы ширина
рендера была примерно 1.6 × целевой ширины движка — запас на последующий кроп
блока нот. Фиксированные 300 dpi (как у Audiveris) на A4 дают больше, чем движок
способен использовать, а на нестандартном листе — либо мало, либо столько, что
лист не влезает в лимиты.

Склейка страниц — `omr/merge.py`. Её главная ловушка: **разное число партий на
страницах**. homr выводит партии из того, что нашёл на конкретном листе, поэтому
«партию 1 к партии 1» склеивать недостаточно — партии разъедутся по длине, и
дальше и music21, и verovio получат рваную партитуру. Выравниваем на общее число
партий, недостающие такты добиваем целотактовыми паузами.

Одной добивки мало, и это видно на том же `pdf-01`: там движок нашёл вторую
партию ровно на одной странице из четырёх, и после выравнивания она состояла из
66 пауз на 76 тактов. Формально корректно, практически — партитура с
инструментом, который молчит почти всю пьесу. Поэтому партия, у которой больше
половины тактов пришлось добить, признаётся артефактом детекции и выбрасывается
(последнюю оставшуюся не трогаем никогда).

## Гранд-стан, ансамбли, басовый ключ

Жалобы «не работают гранд-стан и басовый ключ» разобраны на эталонах
`tests/images/{grand_staff,bass}` (PDF + эталонный MusicXML). Сам движок на
чистом листе читает и то и другое хорошо — терялось на структуре, и почти
везде по нашей вине:

| что было | где чинится | эффект на эталоне |
|---|---|---|
| homr не пишет `<staves>2</staves>`; verovio падает, `repair` (music21) сливает руки в один стан | `api/analysis._declare_staves` | Брамс: фортепиано 16.8% → 98.7%, Шуберт 43% → 98% |
| 0.6.2 склеивает станы в гранд-стан вслепую парами | раннер: `_install_brace_pairing` | Корелли: 4 «фортепиано» → 7 партий |
| в одной системе станов меньше — вся страница идёт одной партией | раннер: `_install_system_rejoin` | Брамс: виолончель 14.5% → 96.6%; Корелли: 285 тактов → 238 (как в эталоне), партии 68–91% → 98–100% |
| рамка страницы режет систему, стан которой не собрался | `stages/page.stray_extent` | фото фагота 90.1% → 99.3% |
| homr падает при выходе, уже записав результат (код -6), — страница выбрасывалась | `engines/homr_engine.run` | Брамс стр. 4 под нагрузкой |
| homr теряет стан (станов меньше, чем у нашего детектора на той же картинке) — пропадает рука целой системы | `recognize._retry_lost_staves`: повтор с размытием 0.7, затем с полями 10% | скриншот Шопена op.10 №3: 79.6% → 91.1% |
| многотактовая пауза у homr — пустой такт нулевой длины: партия вступает раньше, в ансамбле партии разъезжаются | `engines/homr_engine.expand_multi_rests` | Гуно: 70 → 73 такта (как в эталоне) |
| добавочные линейки собирались в «лишний стан» — ложный повтор движка | `staff.drop_ledger_staves` | Барток стр.1, Шопен op.38 стр.2: 11 → 10 станов |
| акколада, слившаяся с чертой системы в один блок на «голос + фортепиано», принималась за скобку ансамбля | раннер: `_brace_decision` | Lieder-превью: фортепиано снова одной партией |

Чего пока не умеем (ограничения самого homr, замерено на эталонах):
октавные линии 8va/8vb — homr пишет написанную высоту, а не звучащую (Барток,
нижний стан: 115 из 394 нот на октаву выше); гранд-стан из двух станов в
скрипичном ключе homr в паре читает с ошибкой на октаву в верхнем стане
(Lieder-превью), хотя по отдельности оба стана читаются верно.

homr 0.7.0 на этих эталонах ХУЖЕ 0.6.2 (его подбор по акколаде путает скобку
системы с акколадой) — обновлять движок без замера нельзя.

Сверка с эталоном — `omr/refcheck.py`, по станам и с диагностикой ключа:

```
python -m omr.refcheck tests/images -o out/
python -m omr.refcheck --compare out/x.musicxml tests/images/bass/x.mxl
```

Две ловушки эталонов, которые он обходит сам: повторы в эталоне бывают
развёрнуты (тогда разворачивается и выход), а эталон бывает фрагментом страницы
(поэтому рядом со строгой `global` считается `fragment`). И главное — мерить
надо и полный путь сервиса: `repair` живёт в `api/`, а не в `omr/`, и главный
дефект был именно там.

## Отчёт

Пайплайн возвращает не только картинку, но и протокол — что сделано и почему:

```
  [+] page+warp    по staff                 уверенность=0.18 было=1562x2402 стало=987x1539
  [+] dewarp       ok                       амплитуда=6.8px дуга=1.0034 линеек=15
  [+] deskew       -0.144°                  проходов=2
  [+] normalize    масштаб x1.93            ширина=1920 интервал=19.8
```

`--debug` дополнительно кладёт картинку после каждой стадии — видно, где именно

## Замер

```
python -m omr.bench photos/ -o bench/ --reference etalons/
```

Каждый снимок гоняется через движок дважды — как есть и после пайплайна — и
сравнивается с эталонным MusicXML по расстоянию Левенштейна на
последовательности `(высота, длительность)` (`omr/score.py`). Считать «сколько
нот нашлось» бесполезно: движок легко выдаёт столько же нот, но не тех.

### Что получилось на синтетическом наборе

Чистый скан (`preprocessing/samples/californication.png`, 10 станов, 15 тактов)
«сфотографирован» под углом на сером столе: перспектива, поворот, неравномерный
свет, JPEG q87, сенсор 3024x4032. Эталон — выход homr на исходном скане, то есть
потолок для этого движка.

| снимок | лист в кадре | как есть | после пайплайна |
|---|---|---|---|
| `fill75` | 75% ширины, наклон 1.5° | 97.0% | **98.5%** |
| `fill55` | 55% ширины, наклон 3° | 97.0% | **98.0%** |
| `fill40` | 40% ширины, наклон -4° | 96.1% | **100.0%** |
| `book` | изгиб страницы у корешка | 77.3% | **96.1%** |
| **среднее** | | **91.9%** | **98.2%** |

Читать это надо так. На аккуратном снимке ровного листа homr и без подготовки
работает хорошо — там выигрыш в пределах пары процентов, и он весь идёт от
масштаба (лист занимает все 1920 px вместо 1440). Настоящая разница появляется
на изогнутой странице: 77% -> 96%, потому что там подготовка чинит то, чего
движок в принципе не умеет починить сам. Заодно видно, что число нот на выходе
(196 -> 203 в среднем) — метрика бесполезная: у `fill40` оно совпадает в обоих
вариантах при разнице в точности в четыре процента.

### На реальных провалах прода

Шесть PNG из архива провалов (`failures_dir`) — то, на чём распознавание падало
в бою. Эталонов для них нет, поэтому смотрим на грубое: получился ли вообще
MusicXML и сколько в нём тактов.

| файл | что не так | как есть | после пайплайна |
|---|---|---|---|
| `123.png` | скан боком (90°) | **движок падает** | 49 тактов, 250 нот |
| `1234.png` | скан боком (90°) | **движок падает** | 33 такта, 86 нот |
| `12233.png` | скан боком (90°) | 1 такт, 1 нота (мусор) | 38 тактов, 173 ноты |
| `2-image2.png` | обычный скан | 14 тактов, 108 нот | 16 тактов, 108 нот |
| `1-image1.png` | обычный скан | 9 тактов, 127 нот | 9 тактов, 126 нот |
| `image0.png` | разворот, 22 стана в кадре | **движок падает** | **движок падает** |
| **итого** | | **3 из 6** | **5 из 6** |

Весь выигрыш здесь дала одна стадия — `orient`. Три файла из шести просто лежали
на боку, и никакая геометрия дальше по конвейеру этого не ловила. На нормальных
сканах (`1-image1`, `2-image2`) пайплайн, как и положено, почти ничего не меняет.

Оставшийся провал — `image0.png`, разворот книги: 22 стана поперёк кадра, после
приведения к 1920 px на межлинейный интервал остаётся 6.5 px. Пайплайн это
диагностирует (`стан слишком мелкий`), но чинится это только разрезом по корешку
(см. «Что дальше»).

### На скриншотах и сканах пайплайн нейтрален

Прогон по тому, что лежит в репозитории (`api/test/a_1.PNG`, `a_2.PNG`,
`preprocessing/samples/*`) — это всё скриншоты и сканы, не фотографии:

```
a_2.PNG              как есть  станов=12 тактов=18 нот=396   пайплайн  станов=12 тактов=18 нот=396
californication.png  как есть  станов=10 тактов=15 нот=203   пайплайн  станов=10 тактов=15 нот=203
hueta.jpg            как есть  станов= 8 тактов=16 нот=267   пайплайн  станов= 8 тактов=16 нот=267
a_1.PNG              как есть  станов= 9 тактов=26 нот=178   пайплайн  станов= 8 тактов=25 нот=174
```

Так и должно быть: там нечего выпрямлять, и стадии честно отказываются
(`[.] dewarp кривизна мала`, `[.] deskew уже ровно`).

### Чего в замерах НЕ хватает

**Настоящих телефонных снимков листа под углом.** В репозитории их нет, в
разобранном архиве провалов тоже — там сканы. Поэтому числа по перспективе и
изгибу получены на синтетике из одной партитуры: они доказывают направление, но
не измеряют качество. Выгрузите из `failures_dir` (`/storage/out/failures`,
таблица `failed_files` в админке) те входы, что были именно фотографиями, и
прогоните `omr.bench` — вот тогда числа будут про ваши данные.

## Что взято у соседей по теме

Смотрел два проекта той же тематики. Новых приёмов не нашлось, но оба подтвердили
принятые здесь решения — что тоже результат.

**[musibot](https://github.com/OmniOMR/musibot)** — веб-сервис OMR, архитектурно
самый близкий сосед. Его пайплайн: найти станы → нарезать страницу на отдельные
станы (`Staves/{n}/image.jpg`) → прогнать по стану модель конкурентно
(`asyncio.TaskGroup`) → склеить в страницу по одной `<part>` на стан. То есть
**единица работы у них — один стан**, и падение одного не уносит страницу. Ровно
тот же принцип независимой единицы применён здесь трижды: try/except вокруг
одного стана в раннере homr, `salvage` по одному такту в `api/analysis.py` и
постраничный PDF. Готовых моделей проект не содержит — это фреймворк
(оркестратор + воркеры + RabbitMQ), брать оттуда нечего.

Полезен их `docs/rough-edges.md` — честный список известных проблем. Один пункт
попадает и в нас: «таймаут только на пайплайн, зависшая модель съедает весь
бюджет». У нас таймаут на движок есть (`homr_timeout_seconds`), но стадии
подготовки не бюджетируются вовсе.

**[OrpheusNet-jianpu](https://github.com/yymmm9/OrpheusNet-jianpu)** —
распознавание цзянпу, цифровой нотации без нотоносцев. Прямо не применимо, но
две его развилки совпадают с нашими: связные компоненты вместо проекций «как
более устойчивые на наклонных и шумных страницах» (в `omr/staff.py` выбрано то
же самое) и «сначала дешёвый OCR, CNN только в откат» — та же лесенка
«дешёвая проверка → дорогой фолбэк», что у нас в `renders_ok → repair → salvage`.
Их горизонтальная проекция для отделения строк от текста и метаданных —
кандидат на разрез разворота по корешку, если браться за `spread`.

## Что дальше

По убыванию пользы, судя по разбору архива провалов:

* **Переворот на 180°.** Стадия `orient` ловит только поворот на 90°. Вверх
  ногами страница даёт такие же горизонтальные линейки; отличить можно по
  положению ключа относительно стана или OCR заголовка.
* **Версия движка.** В `api/requirements.txt` homr закреплён на `0.6.2`, на PyPI
  уже `0.7.0` (там же снято ограничение Python `<3.13`, из-за которого в
  `pyproject.toml` стоит `requires-python = ">=3.12,<3.13"`). Пайплайну версия
  безразлична, обновление стоит проверить отдельным замером.
* **Подключение к API.** Здесь ничего не тронуто: `api/services.py` по-прежнему
  отдаёт homr исходный файл. Врезка — одна строка в `process_single` перед
  `homr_service.run`: прогнать снимок через `omr.prepare` и передать движку
  результат. Делать это стоит после замера на своих данных.
