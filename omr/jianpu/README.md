# `omr/jianpu` — цзянпу (简谱): эталоны и распознавание

Цзянпу — цифровая нотация без нотного стана: ступени лада цифрами 1–7, октава
точками над и под цифрой, длительность подчёркиваниями и тире, текст строками
куплетов под нотами. Нотный движок (homr) такой лист не читает вовсе.

Распознаёт движок из [jpeditor](https://github.com/lodebar2026/jpeditor) (MIT),
подключённый внешним процессом, как homr. Эталоны для замеров делаем сами —
генератором, который проверяет каждую пару.

```
scripts/build_jpeditor_omr.sh                                    # собрать движок в vendor/
python -m omr.jianpu.recognize score.pdf -o out/                 # распознать
python -m omr.jianpu.bench tests/images/jianpu/synth -o out/b    # замерить на эталонах
python -m omr.jianpu.synth essen:han1 -o tests/images/jianpu/synth --limit 10   # новые эталоны
```

В API — пресет `jianpu` (`api/jianpu.py`), для одиночной задачи и для плейлиста.

---

## Движок: jpeditor

Что внутри: геометрия связных компонент (цифры, подчёркивания, октавные точки,
тире, лиги, вольты) плюс PaddleOCR v6 через onnxruntime для цифр, текста и
заголовка. TypeScript, CLI на Node без браузера.

| где | что |
|---|---|
| `scripts/build_jpeditor_omr.sh` | собирает самодостаточный пакет (omr-cli.mjs, модели, node_modules под платформу, ~98 МБ) из **закреплённого коммита**. Обновлять коммит — только с замером `omr.jianpu.bench` |
| `vendor/jpeditor-omr` | локальная сборка (в git не идёт) |
| образ | стадия `jpeditor` в Dockerfile собирает пакет в `/opt/jpeditor-omr`, в рабочий образ копируются пакет и `node` |
| `omr/engines/jianpu_engine.py` | обёртка: все страницы задачи одним запуском (загрузка модели ~2.4 с, страница ~0.3–1 с), провал одной страницы не роняет остальные |
| `omr/engines/_jianpu_runner.mjs` | свой раннер вместо CLI пакета: кроме MusicXML отдаёт все строки заголовка листа (см. «Темп») |
| `omr/jianpu/tempo.py` | темп и название из строк заголовка |
| `omr/jianpu/recognize.py` | PDF постранично (pypdfium2), HEIC и снимки с EXIF-поворотом — в PNG, склейка страниц `omr.merge` |
| `omr/jianpu/voices.py` | отказ до движка, если на листе многоголосие (хор, дуэт) — см. ниже |
| `api/jianpu.py` | пресет `jianpu`: мимо homr и Audiveris, без отката на homr; таймаут `JIANPU_TIMEOUT_SECONDS` (180 с) |

Каталог пакета: `OMR_JIANPU_PACKAGE`, иначе `/opt/jpeditor-omr`, иначе
`vendor/jpeditor-omr`; Node — `OMR_NODE` или `node` из PATH.

Нотный пайплайн `omr/recognize.py` для цзянпу не используется. Вся его
геометрия — поворот, рамка страницы, dewarp — держится на нотных линейках, а у
цзянпу их нет. Общее у них — растр PDF и склейка страниц.

Две детали обёртки, без которых было бы хуже:

* **входы копируются под номерами.** Выход движок называет по имени входа, и два
  `image0.png` из разных папок плейлиста затёрли бы друг друга;
* **EXIF.** sharp в движке ориентацию из EXIF не применяет: телефонный снимок с
  пометкой «повернуть» пришёл бы к нему боком. Такие снимки уходят в PNG уже
  повёрнутыми.

### Хоры и дуэты: отказ до движка

Движок многоголосия не знает: строки голосов одной системы он читает подряд как
одну мелодию. Хор SATB превращался в одну партию с размером 6/2 и уходил клиенту
как успех. Теперь `voices.py` проверяет каждую страницу до движка. Если
многоголосная хоть одна, отказ получает вся песня: хор без одной страницы — та же
негодная партитура, только короче.

Признак — вертикаль через несколько строк текста. Сама по себе длинная линия
признаком не является, и ложные срабатывания по дороге были настоящие:

| что | как отличаем | на чём видно |
|---|---|---|
| скобка голосов слева от системы | не выше 70% листа, справа от неё ≥ 2 строк, и почти весь текст этих строк правее | хор из набора |
| сквозная тактовая черта | через ≥ 2 строк, текст по обе стороны; нужно три таких | так пишет часть издателей; живого примера пока нет |
| рамка вокруг текста | у левой вертикали есть парная той же высоты правее — не скобка | тест |
| край кадра на фото | вертикали у самого края изображения не считаются | `image0.png`: тёмная полоса у левого края давала «скобку через 11 строк» |
| столбец иероглифов | линии ищутся только среди вытянутых по вертикали компонент | семь плотных куплетов `jiangsu2_1026` Хаф собирал в «черту через 5 строк» |

Отказ — если скобок голосов две и больше, или одна через ≥ 3 строк, или
сквозных черт ≥ 3.

Замер. Хор — 10 страниц из 10: пять JPG (так их положил в PDF телефон) и они же
растром pypdfium. Один голос — 83 страницы из 83, и ни на одной не найдено даже
одиночной скобки или черты: 3 реальных листа, 40 синтетических PNG из LilyPond и
те же 40 растром 2480 px. Проверка стоит до 0.1 с на страницу.

Чего не ловит: фигурную скобку «{» (фортепиано в две строки) — она не прямая,
и сквозные черты на живом листе пока не проверены.

### Темп

Где он на листе: в начале, слева сверху — сразу после «1=C 3/4» или строкой под
ними. Пишут метрономом (`♩=72`) или словом: итальянским термином, его китайским
названием (中板 — Moderato) или простым 中速 «умеренно», часто вместе с характером
(«中速 深情地»). 散板 (знак «サ») — свободный ритм без темпа.

Что читает движок: из заголовка — только метроном. Строку со словом он
выбрасывает, а набранную крупно делает **названием** («中速深情地» вместо
«梦里故乡»). Все строки заголовка он печатает лишь в отладке (`__omrDebug`,
метка `[header/det]`) — наш раннер `_jianpu_runner.mjs` эту печать перехватывает
и кладёт рядом с MusicXML, как `_homr_runner.py` перехватывает OCR над станом.

Дальше `tempo.py`, по порядку: метроном (число написано явно); 散板 — темп не
ставится; слово — по учебной шкале, с пометкой в логе «оценка по слову». Темп
пишется в первый такт как `<words>中速</words>` + `<sound tempo="88"/>`, его и
берёт `collect_bpm` в API.

Шкала — одно число на термин. Единого стандарта нет: у 行板 в учебных таблицах 66,
в китайской Википедии 76–108, даже 慢板 одни относят к Lento, другие к Adagio.
Взята распространённая учебная ([搜狗问问](https://wenwen.sogou.com/question/q758710669.htm),
[豆瓣](https://www.douban.com/note/604733552/); сверено с
[sohu](https://www.sohu.com/a/448393095_120051694) и
[维基百科](https://zh.wikipedia.org/zh-hans/%E9%80%9F%E5%BA%A6_(%E9%9F%B3%E6%A8%82))):

| 广板 Largo | 慢板 Lento | 柔板 Adagio | 行板 Andante | 小行板 Andantino | 中板 Moderato | 小快板 Allegretto | 快板 Allegro | 急板 Presto |
|---|---|---|---|---|---|---|---|---|
| 46 | 52 | 56 | 66 | 69 | 88 | 108 | 132 | 184 |

У простых слов чисел в источниках нет — они приравнены к ближайшему по смыслу
термину: 慢速 → 慢板, 稍慢 → 行板, 中速 → 中板, 稍快 → 小快板, 快速 → 快板.

Название. Если движок сделал названием строку темпа, настоящее берётся из строк
заголовка — самая крупная строка из иероглифов, не ниже захватчика, не
тональность, не «作词/作曲». У пьесы «如歌的行板» 行板 — часть названия, и строкой
темпа его не читаем.

Замер: на листе 梦里故乡 дорисованы по очереди все термины шкалы, простые слова,
«中速 深情地», `♩=72`, 散板, Moderato — строкой под «1=C 3/4», и «中速» в строке
размера. 19 из 19: темп по шкале, 散板 без темпа, название «梦里故乡» везде на месте.

Чего не читает: метроном над первым тактом, а не в заголовке (на странице для эрху
`♩=66` стоит над вторым тактом — ниже зоны заголовка движка), смены темпа по
ходу пьесы, характер без темпа («深情地» отдельно). Замер — на дорисованном тексте,
живых листов со словом темпа в наборе пока нет.

## Эталоны: синтетика, которая проверяет сама себя

Готовых пар «лист цзянпу + эталонный MusicXML» в открытом доступе нет, поэтому
их делает `synth.py`: мелодия -> текст jianpu-ly (`.jly`) -> LilyPond -> PDF.
Эталонный MusicXML пишется из той же модели (`melody.py`), и соответствие листа
эталону проверяется: LilyPond из того же `.ly` строит MIDI, и он сверяется с
эталоном нота в ноту (высота, начало, длительность). Не совпало — пара не пишется.

Проверка не формальная. Она поймала полулигу у источника: jianpu-ly рисует лигу
по её началу, а эталон сливал звук по концу (`jiangsu1_119`). Поймала и
недописанный последний такт, и расхождение октав с jianpu-ly (о нём ниже).

Импортом MusicXML самого jianpu-ly генератор не пользуется: на Anthology тот
падал в 48 песнях из 160, а смену размера посреди пьесы не держит вовсе.
Текстовый ввод jianpu-ly эти случаи держит, поэтому `.jly` пишется свой.

Нужны `brew install lilypond` и `uv tool install jianpu-ly`.

### Источники мелодий

* `essen:han1`, `essen:han2` — 1224 китайские народные песни из корпуса Essen,
  который лежит внутри music21. Ритм чистый, смены размера настоящие, текста нет.
* Anthology — MusicXML с текстом (Цзянсу I и II: 1–7 куплетов). Только MusicXML,
  без 8 тысяч PNG:

  ```
  git clone --filter=blob:none --sparse https://github.com/m-july/Anthology-of-Chinese-Folk-Songs-v251103 anthology
  cd anthology && git sparse-checkout set --no-cone '/lyrics-included/jiangsu*/*.musicxml'
  ```

  Проходит примерно каждая пятая песня: у остальных такты, которых в цзянпу не
  бывает (5/2, 7/4, 9/16), — ошибки ритма их распознавания. Лицензии у
  репозитория нет, статья под CC BY-NC-SA 4.0 — данные только для замеров.

### Что генератор делает с мелодией — `melody.prepare`

| шаг | зачем |
|---|---|
| размер каждого такта — по его фактической длине; короткий первый такт — затакт | у Anthology в каждом такте 4/4 при фактических 2/4 и 3/4 |
| короткий последний такт получает свой размер | недописанный такт LilyPond отмечает «bar check failed», от настоящей ошибки не отличить |
| мелодия сдвигается на целые октавы к минимуму точек | абсолютной октавы в цзянпу не видно; песня в 1=G вокруг G4 иначе вышла бы с точкой над каждой цифрой |
| длительности режутся на знаки под лигой; пауза длиннее четверти — «0 0» | эталон совпадает с листом знак в знак, иначе `refcheck` штрафует правильное чтение |
| лига остаётся только с обоими концами | полулигу jianpu-ly и эталон понимают по-разному |
| ноты нулевой длины выбрасываются, как форшлаги | они в каждой седьмой песне Anthology |
| одна ступень с разными знаками в такте — пропуск | как jianpu-ly рисует бекар, не проверено |

Вёрстка варьируется детерминированно от имени пары: кегль 17–26, A4 или A5,
номера тактов, «1=F 2/4» в углу листа или дробью у первого такта, китайский
шрифт текста и цифр из установленных. PDF — через cairo: ghostscript встраивает
китайский шрифт целиком (885 КБ на лист против 45 КБ). Блок `set-global-fonts`,
который jianpu-ly вставляет на macOS, из `.ly` вырезается: в LilyPond 2.24+ его нет.

### Октава — договорённость движка

Точки отсчитываются от «средней» тоники, и где она, лист не говорит. Правил три:

| кто | тоника без точек |
|---|---|
| jpeditor (`jpPitch`) — **наша договорённость** | 4-я октава; при букве тоники B (1=B, 1=Bb) — 3-я |
| jianpu-ly | 4-я при буквах C–F, 3-я при G–B |
| «всегда 4-я» (было у нас сначала) | — |

Берём правило движка. Переписывать его выход ради своей договорённости значило бы
держать ещё одно место, где можно ошибиться. Поправку на jianpu-ly делает сверка
в `synth.py`. С прежним правилом «всегда 4-я» бенчмарк показывал ровно октаву
расхождения в песнях 1=Bb, теперь сдвигов нет.

### Набор `tests/images/jianpu/synth`

40 пар: PDF, `.musicxml` и `.jly` — исходник листа текстом, удобно смотреть, что
нарисовано. 20 из Essen (`han1_*`, `han2_*`: без текста, 8 тональностей, смены
размера), 20 из Anthology (`jiangsu1_*`, `jiangsu2_*`: 1–7 куплетов, все в 1=C).
Всё вместе — 2 МБ. `*.musicxml` в корне `.gitignore` игнорируется, для этой папки
сделано исключение.

`python -m omr.refcheck tests/images` папки `jianpu` пропускает: нотный движок
цзянпу не читает.

## Что дальше

1. **Хоры и многоголосие.** Сейчас честный отказ (`voices.py`). Распознавать их —
   значит резать систему на голоса по скобке, гнать движок по каждому голосу
   отдельно и склеивать голоса в партии.
2. **Эталоны реальных листов.** Синтетика — одна вёрстка LilyPond; реальные листы —
   другие шрифты, фото, скриншоты из приложений. Набирать их удобнее всего `.jly`
   (понадобится разбор `.jly` в `melody.py`) и сличать рендер с оригиналом.
3. **Фото.** В наборе пока только чистые листы.
4. **Инструментальные сборники** (аппликатура, штрихи над цифрами) движок не берёт.
5. **Темп внутри нот:** метроном над тактом и смены темпа по ходу пьесы.
