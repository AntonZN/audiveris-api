# `zeus_eval` — оценка второго движка OMR

> Каталог называется `zeus_eval`, а не `zeus`: пакет с именем `zeus` на
> PYTHONPATH перекрывает саму библиотеку Zeus, и её CLI падает с
> «No module named 'zeus.cli'».

Проба [Zeus](https://github.com/OmniOMR/zeus) как альтернативы homr. Zeus — это
модель из статьи Mayer et al., ICDAR 2024 «Practical End-to-End Optical Music
Recognition for Pianoform Music»; тот самый «staff-transcriptor», который в
документации [musibot](https://github.com/OmniOMR/musibot) фигурирует абстрактным
примером (musibot — фреймворк оркестрации, Zeus — сама модель).

> **Статус: стенд, в прод не идёт.** Замер показал паритет с homr в лучшем случае
> (подробности ниже), поэтому Zeus остаётся здесь как задокументированный
> результат оценки, а не как рабочий движок. Группировка станов в системы и
> нарезка кропов лежат в `zeus_eval/systems.py`, а не в `omr/`, именно поэтому:
> продовому пакету они не нужны — homr гранд-станы группирует сам.

## Почему отдельный модуль со своим образом

Zeus требует **Python строго `>=3.10,<3.11`** и **TensorFlow ~2.12** (2023 год).
В окружении API стоит Python 3.12+, а homr там работает на чистом ONNX без
тяжёлых зависимостей — тащить туда вторую версию Python и TensorFlow незачем.
Поэтому Zeus живёт в своём образе, а стыкуется с проектом через пакет `omr`,
который копируется внутрь.

Проверка колёс TF 2.12 (важно для развёртывания):

| платформа | есть колесо |
|---|---|
| `manylinux_2_17_x86_64` (докер, amd64) | да |
| `manylinux_2_17_aarch64` (докер, arm64) | да |
| macOS arm64 | только через `tensorflow-macos`, не через `tensorflow` |

Отсюда и решение: тестируем в докере, а не локально.

## Как стыкуется с `omr`

Zeus читает **один стан за раз** и ждёт на входе «cropped and roughly deskewed
single staff». Полную страницу ему давать нельзя — получится мусор. Это ровно
тот вход, который производит наш пайплайн, так что разделение обязанностей
выходит естественным:

```
снимок
  |
  |  omr: ориентация -> разворот -> рамка страницы -> гомография
  |       -> dewarp -> доворот -> свет и масштаб
  v
ровная страница
  |
  |  omr.staff.analyse      -> станы
  |  zeus_eval.systems.group_into_systems -> гранд-станы парами
  |  zeus_eval.systems.crop_systems       -> по картинке на систему
  v
кропы станов --> zeus predict --> MusicXML на стан
                                        |
                                        |  omr.merge.merge
                                        v
                                  страница целиком
```

Отличие от homr: тот ищет станы сам, а Zeus полагается на наши. Склейка станов в
страницу — тем же `omr.merge`, что и склейка страниц: операция та же, дописать
такты в хвост партии и перенумеровать.

## Запуск

```bash
docker compose -f zeus_eval/docker-compose.yml build

# одна страница
docker compose -f zeus_eval/docker-compose.yml run --rm zeus \
    /data/fail/phone-01-angled-sheet.png -o /out

# каталог целиком
docker compose -f zeus_eval/docker-compose.yml run --rm zeus \
    /data/success/*.jpg -o /out --keep-crops
```

Каталоги `fail_prod_files` и `success_prod_files` смонтированы в `/data/fail` и
`/data/success` **только на чтение**; всё, что контейнер создаёт, уходит в `/out`
(на хосте — `zeus_eval/out`).

`--keep-crops` оставляет нарезанные станы рядом с результатом: если движок на
чём-то споткнулся, первым делом надо смотреть именно на кроп.

## Снапшоты моделей

Лежат **не** в релизах репозитория zeus (там пусто), а в соседних репозиториях
авторов. В образ кладутся две:

| файл | размер | чем обучена |
|---|---|---|
| `ayce-2026-08-03.model` | 26 МБ | Dolores + OLiMPiC + OmniOMR (соло-стан, свежая) |
| `zeus-camera-grandstaff-lmx-1.0-2024-02-12.model` | 27 МБ | Camera GrandStaff — **сфотографированные** ноты |

По умолчанию берётся `ayce-2026-08-03`. Выбор — флагом `--model`.

## Что показал замер

Группировка станов в гранд-станы сделана (`omr.staff.group_into_systems`), так что
камерную модель удалось попробовать честно. Итог: **обе модели пока не лучше
homr**, и у каждой свой характерный отказ.

| файл | homr | Zeus solo | Zeus camera |
|---|---|---|---|
| `rot90-01-ballando` (однолинейная) | 49 т / 250 н | 50 т / 251 н | 7 систем из 10 |
| `scan-01-jp-vocal` (гранд-стан) | 9 т | 9 т | 1 система из 4 |
| `hueta` (гранд-стан) | 16 т | 13 т | 2 системы из 5 |

**Соло-модель** на однолинейной музыке идёт нота в ноту с homr, но срывается в
цикл на незнакомом входе: кроп с МНОГОТАКТОВОЙ ПАУЗОЙ (толстая полоса, «4»
сверху) дал 174 одинаковых пустых такта при 4-6 у соседей, и склеенная страница
раздулась с 38 тактов до 206. Лечится обрезкой до медианы по соседям
(`_clamp_runaway_staves`); срыв всегда упирается в 171-174 такта — это предел
декодера.

**Камерная модель** гранд-стан действительно читает: в её выводе есть
`clef:G2 staff:1 clef:G2 staff:2`, `voice:1`/`voice:2`, `backup`. Но
последовательности **обрываются на полуслове**, и декодер LMX->MusicXML падает с
`Onset must be non-negative` — незакрытый `backup` даёт отрицательную позицию.
Причём дело не в числе тактов: кропы гранд-станов `scan-01` содержат по 2.2
такта и проходят 1 из 4, а одностановые кропы `ballando` по 4.9 такта проходят
7 из 10. Гранд-стан просто порождает вдвое больше токенов (два нотоносца
чередуются через `backup`), и модель упирается в бюджет декодирования.

Вывод: чтобы использовать грандстановые модели Zeus, систему надо резать ещё и
по тактам — их обучающий набор GrandStaff состоит из коротких фрагментов, а не
из полноширинных систем. Это следующий слой (нужна детекция тактовых черт).

## Что проверить в первую очередь

* **Бинаризацию.** Модели 2024 года помечены как B/W. Для homr бинаризовать вход
  категорически нельзя (см. `omr/README.md`), здесь может быть наоборот — это
  первое, что стоит померить.
* **Грандстаны.** `omr.crop` режет по одному стану; для фортепианной музыки
  правильнее отдавать пару нотоносцев целиком.
* **Сравнение с homr** на одних и тех же кропах, по нотам через `omr/score.py`.
  Публикация ICDAR — хороший признак, но не доказательство на наших файлах.
